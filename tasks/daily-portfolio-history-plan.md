# Daily portfolio history — proposed plan

Status: Daily history and background backfill are implemented; corporate-action reconciliation and comprehensive failure/concurrency verification remain pending. The user accepts the adjusted-price assumption and wants gaps or incomplete coverage surfaced.

Review follow-up: new partial FYERS responses are split into available and unavailable weekday intervals; BSE fallback handles no saved NSE prices, and sync reads saved dates for a bounded candidate range. At the user's request, the chart uses observed dates to avoid breaks on market holidays; it may connect across dates missing all prices until a reliable trading calendar is available. Existing complete coverage still needs a safe audit and repair. Live database/provider integration and concurrency testing remain pending.

## Outcome

Show the market value of recorded stock and ETF holdings at each available daily close. Retain history after sales; quantities fall on the sale date and proceeds are excluded because brokerage cash is not tracked. The line measures holdings value, not investment return. Preserve the existing latest-quote flow and clearly distinguish any intraday point from completed closes.

## Decisions

- Keep per-portfolio daily closes keyed by instrument and market date, with exact decimal prices, source and adjustment basis. Add sync coverage/job state with bounded date windows, retries, and unique keys. Do not delete historical closes on sale.
- Backfill from the first recorded purchase, including subsequently sold instruments, within FYERS entitlement. Flag data before the provider's earliest available date and provider errors as unavailable; never fill missing held-symbol prices with purchase cost or a partial sum.
- Confirm FYERS per-request date range, retention rights and corporate-action adjustment semantics before enabling historical calculations. Reconcile adjusted prices and ledger quantities; show unsupported intervals as unavailable rather than fabricate prices.
- The user says existing entries already account for splits and bonuses; treat the recorded transactions as authoritative and never automatically apply the same quantity change again. Future manual entries remain user-controlled. A normal buy is not a general corporate-action operation and must not be presented as one without supporting correct cost and quantity semantics.
- The user may delete an original purchase and replace it with a normalized quantity and unit cost. This preserves the chosen total cost but overwrites original transaction history and does not reliably reconstruct actual past share counts; adjusted FYERS prices and recorded quantities must still be on a consistent basis. Treat unsupported history as incomplete. A 2:1 split doubles the shares, while a 2:1 bonus conventionally grants two additional shares per existing share.
- Corporate-action information may be shown on the instrument detail page when a reliable supported provider supplies it; omit the section or show it unavailable otherwise. FYERS' documented History and Reports APIs did not expose a dedicated corporate-actions endpoint when reviewed. Its app report is a separate feature, not evidence of API access. Add a portfolio-scoped corporate-action metadata table only when a supported source and its fields are verified. Metadata must not automatically mutate holdings. Retain room for future dividend events; actual dividend receipts and payments need separate user-scoped cash-flow records and are not inferred from announcements.
- FYERS documents a 366-day limit for daily-candle requests and recommends caching historical ranges. A FYERS community response says historical data is adjusted for corporate actions; the affected event types, adjustment factors, revision behavior and compatibility with recorded historical quantities are not established. In particular, retaining a pre-action cached price without refetching could mix adjustment bases. Treat this as unresolved before presenting historical totals. Sources: https://fyers.in/api-docs/v3/api/market-data/historical-data and https://fyers.in/community/t/how-can-we-retrieve-historical-stock-data-from-fyers-api-with-all-corporate-actions-adjusted-splits-bonus-merger-demerger-etc/22650
- Incrementally fetch missing ranges without re-requesting already stored historical data; record empty successfully checked intervals separately from failures. Do not store an unfinished candle as a completed close. Share the existing cross-instance request limiter and retry 429 responses.
- Use a durable, portfolio-scoped queue of bounded work. Dashboard requests process short units using the current owner-bound FYERS cookie and persist checkpoints; subsequent authenticated requests resume. Closing the page stops further processing until a later visit; expired sessions require reconnect. Do not promise autonomous work. Prevent concurrent claims and duplicate writes. No tokens are stored in the queue.
- Process recent windows first for a useful initial chart, then older windows. Show cached data immediately, with loading/progress and incomplete, unavailable and reconnect states. Only call FYERS for missing/stale coverage.
- Reconstruct daily end-of-day quantities from all recorded buys and sells, including fully sold instruments. Same-day transactions use the existing ledger order and affect that day's closing quantity. For each day, sum quantity times closing price using decimal arithmetic. Maintain zero holdings as zero; carry a prior close only for a confirmed non-trading or symbol non-trading session and label its actual date; unknown gaps remain unavailable.
- Filter by actual calendar dates (7D, 30D, 3M, 6M, 1Y, All), preserve boundary context only when supported, and aggregate on the server. Use daily points, no invented intermediate values, no permanent peak/trough markers, and a date/value hover and keyboard-accessible alternative. Identify partial coverage and market-close dates. Current quote is an explicitly dated optional latest point with complete coverage and consistent dates.
- Preserve dated price observations and user ledger; no implicit conversion to total-return, P&L, or cash-inclusive account value. Do not show an unadjusted percentage as investment return. Do not implement dividends, cash balances or other asset classes in this slice.
- Use the 1 GB project budget. Estimate 50,000 daily rows for 40 symbols over five years; provisional planning allowance 5–15 MB including index, subject to actual measured table size, indexes and Neon accounting. Storage and FYERS rights must be verified.

## Delivery slices

1. **Provider and data contract.** Verify entitlement, single-request date span, timestamp/trading-date interpretation, adjustment/retention rights, holidays and existing data completeness. Define unavailable behavior. Verification: recorded provider evidence and representative documented fixtures. No migration until unresolved accuracy issues have safe fallback.
2. **Schema and one-symbol backfill.** Add versioned migration for scoped daily prices and sync work state; authorize reads and upserts. Fetch bounded historical windows for one symbol, persist progress and resume after interruptions. Verification: isolated database tests for ownership, idempotency, partial failures and empty windows.
3. **Daily portfolio valuation.** Reconstruct quantities from the ledger and compute fully covered daily totals. Include sold instruments and same-day trades; reject misleading partial valuations and conflicting adjustments. Verification: decimal fixture tests for purchases, partial/full sales, repurchases, gaps, dates, corporate actions and multiple users.
4. **Dashboard chart.** Render cached daily totals, calendar ranges and accessible tooltip/alternative; remove persistent markers and distinguish latest quote, gaps and sync status. Verification: browser checks for desktop/mobile, keyboard, loading, empty, stale and reconnect states; reconcile selected dates against manually calculated fixtures.
5. **Incremental synchronization.** Expand bounded resumable work to all needed symbols; prioritize recent ranges; coordinate concurrent sessions and provider limits. Verification: mocks for 429, expired token, duplicates, crashes, interrupted page visits and concurrent requests; prove a week-later refresh asks only for missing windows.
6. **Operational and documentation review.** Measure storage on a representative isolated dataset, review usage against the budget, update README, AGENTS.md, PRODUCT.md, technical specification and task status; run unit, lint, formatting, typecheck and build checks. Confirm retention rights and deploy migration separately before enabling the feature.

## Review checkpoint

User approval is required before implementation. Main risks: FYERS corporate-action basis and redistribution/retention terms; missing five-year history; owner session expiry; and incomplete historical records. Historical access and execution limits should be rechecked when implementation starts.
